# Sim2Real Website

Developer handoff guide for the Sim2Real robotics competition website. The application is a server-rendered Django project that supports the public event site, participant accounts and profiles, team registration and payment verification, organiser announcements, problem statements and resources, submission windows, quizzes, and support queries.

## Current state

- Framework: Django 5.1.7
- Runtime used by the checked-in bytecode: Python 3.12 (Python 3.12 is the safest local choice)
- Database: SQLite
- Front end: Django templates, CSS, and vanilla JavaScript
- Production entry point: `simreal.wsgi:application` (Gunicorn is listed as a dependency)
- Automated tests: test modules exist, but they currently contain no substantive tests

The repository is usable as an application prototype, but it needs the production-hardening work listed in [Known issues and handoff priorities](#known-issues-and-handoff-priorities) before a public deployment.

## Application map

| Package | Responsibility | Main URL prefix |
| --- | --- | --- |
| `landing_page` | Public landing page, sponsor page, public contact forms, robots.txt, and sitemap | `/` |
| `accounts` | Login, signup, email verification, and OTP password reset | `/accounts/` |
| `user_profile` | Participant profile details and profile photo | `/user/user_profile/` |
| `team_profile` | Team creation/joining, join requests, event registration, and payment proof | `/user/team/` |
| `home` | Authenticated participant dashboard, announcements, resources, problem statement, and submissions | `/user/` |
| `queries` | Authenticated participant support tickets and responses | `/user/query/` |
| `staff_home` | Organiser dashboard and event administration | `/staff/` |
| `simreal` | Project settings, root routing, WSGI/ASGI entry points, and optional maintenance middleware | n/a |

The project uses Django's built-in `User`. A related `accounts.UserRole` record distinguishes organisers from participants. Participant pages also require a complete `UserProfile` in several flows.

## Local setup

### Prerequisites

- Git
- Python 3.12
- A Gmail-compatible SMTP account if signup, account verification, or password reset must work locally

### 1. Clone and create an environment

```bash
git clone https://github.com/Sim2Real-lab/Sim2Real-master-repo.git
cd Sim2Real-master-repo

python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
```

On Windows PowerShell, activate the environment with:

```powershell
.venv\Scripts\Activate.ps1
```

### 2. Install dependencies

```bash
python -m pip install -r requirements.txt
python -m pip install python-dotenv Pillow
```

`python-dotenv` and Pillow are required by `simreal/settings.py` and the image fields respectively, but are not yet included in `requirements.txt`. The second command is therefore required until the dependency file is corrected.

### 3. Configure the environment

Create `.env` in the repository root:

```dotenv
SECRET_KEY=replace-with-a-long-random-development-key
ALLOWED_HOSTS=localhost,127.0.0.1

# Required for signup verification and password-reset OTP email.
EMAIL_HOST=smtp.gmail.com
EMAIL_PORT=587
EMAIL_USE_TLS=True
EMAIL_HOST_USER=your-sender@example.com
EMAIL_HOST_PASSWORD=your-app-password
```

Do not commit `.env`. For Gmail, use an app password rather than an account password. The current settings always select Django's SMTP backend; if email is not configured, ordinary browsing still works, but signup and password-reset email will fail.

### 4. Initialize and run

```bash
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Open <http://127.0.0.1:8000/>. The Django admin is at <http://127.0.0.1:8000/admin/>.

### 5. Create an organiser account

Creating a user also creates an associated `UserRole` through a post-save signal. In Django admin:

1. Open the relevant `UserRole` record.
2. Enable `is_organiser` for an event organiser.
3. Ensure the account has a completed `UserProfile` if the target view uses the profile-completeness guard.

`is_staff` controls access to Django admin; `UserRole.is_organiser` controls access to the custom `/staff/` interface. They are separate permissions.

## Common development commands

```bash
# Framework and configuration checks
python manage.py check

# Run the test suite
python manage.py test

# Create and apply model migrations
python manage.py makemigrations
python manage.py migrate

# Build the static asset directory for deployment
python manage.py collectstatic --noinput

# Remove unverified accounts older than the command's cutoff
python manage.py delete_unverified_users
```

When changing a model, commit the generated migration with the code change. Do not hand-edit `staticfiles/`; it is generated by `collectstatic`. Source assets live inside each app's `static/` directory.

## Core workflows and data

### Participant flow

1. A participant signs up with an email address (stored as both username and email).
2. The account remains inactive until the verification link is used.
3. The participant logs in and completes `UserProfile`.
4. They create or join a team of up to three members.
5. The team registers, uploads payment proof when required, and waits for organiser verification.
6. Verified teams can use event resources, submission windows, and tests exposed by organisers.

### Organiser flow

The `/staff/` dashboard provides interfaces for participant and team review, payment verification, announcements, problem-statement sections, resources and brochures, submission windows and grading, support-ticket responses, and tests/questions/results.

### Important model relationships

- `User` → one `UserRole` and one participant `UserProfile`
- `Team` → one leader, many members, join requests, payment state, and submissions
- `SubmissionWindow` → many team `Submission` records
- `Test` → many `Question` records; `ParticipantTest` → many `ParticipantAnswer` records
- `ProblemStatementConfig` → ordered `ProblemStatementSection` records
- `queries.Query` → participant/sponsor ticket, optional organiser responder, and response

## Static files, uploads, and deployment

For a production-style run:

```bash
python manage.py check --deploy
python manage.py migrate
python manage.py collectstatic --noinput
gunicorn simreal.wsgi:application --bind 0.0.0.0:8000
```

A reverse proxy or platform service must serve `/static/` from `staticfiles/`. User uploads (profile photos, payment screenshots, problem statements, resources, and brochures) also require durable storage and explicit `MEDIA_ROOT`/`MEDIA_URL` configuration; that configuration is currently missing.

SQLite is appropriate for a single-developer environment. Before multi-instance or production deployment, move to a managed relational database and configure backups. Preserve both the database and uploaded media during migrations.

## Known issues and handoff priorities

Address these in roughly this order:

1. **Fix production settings.** `DEBUG` is currently the string `"true"`, so it is always truthy. Remove the unsafe fallback secret, parse environment booleans correctly, set production hosts, and enable secure cookie/HTTPS settings.
2. **Complete dependency declarations.** Add `python-dotenv` and Pillow to `requirements.txt`, pin Gunicorn, and remove unused packages after verifying imports.
3. **Configure uploaded media.** Add `MEDIA_ROOT` and `MEDIA_URL`, development URL serving, and durable production object/file storage. Uploaded files are central to several workflows.
4. **Add meaningful tests.** Prioritize account activation and OTP expiry, role/profile decorators, team-size and registration rules, payment verification, submission-window timing, quiz grading, and access control.
5. **Clean generated files from Git.** Compiled `__pycache__` files and collected `staticfiles/` are tracked. The `.gitignore` is UTF-16 encoded and should be normalized to UTF-8 before removing generated artifacts in a dedicated cleanup change.
6. **Resolve legacy/duplicate structure.** `home.models.Team` overlaps conceptually with the active `team_profile.Team`; team URL patterns are included through more than one route; and several decorator implementations are duplicated. Confirm data compatibility before consolidation.
7. **Make event year configurable.** Several models default to `2025`; move the active event year to configuration or a dedicated event model.
8. **Define deployment operations.** There is no checked-in container, service definition, CI pipeline, health check, backup policy, or documented hosting architecture.

## Change checklist

Before handing a change to another developer:

```bash
python manage.py check
python manage.py makemigrations --check
python manage.py test
git status --short
```

Also verify the affected workflow with both a participant account and an organiser account when permissions are involved. Never commit `.env`, database files, uploaded media, SMTP credentials, or production secrets.
